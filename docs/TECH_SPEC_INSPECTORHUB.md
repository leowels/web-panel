# Техническое задание (ТЗ)
## Проект: InspectorHub
## Версия: 1.0
## Дата: 13.02.2026

## 1. Назначение системы
InspectorHub — веб-система для управления промышленными инспекциями, нарушениями, актами и рисками по оборудованию с поддержкой AI-помощника, карты цеха, SLA-контроля и аудита действий.

## 2. Цели проекта
1. Централизовать учет оборудования, инспекций и нарушений.
2. Снизить риск пропуска критичных нарушений за счет SLA-алертов и риск-скоринга.
3. Обеспечить прослеживаемость действий пользователей и системных ошибок.
4. Ускорить работу инспектора за счет AI-рекомендаций и базы знаний.
5. Обеспечить формирование отчетов и экспорт данных в понятном виде.

## 3. Границы проекта
### Входит в проект
1. Web frontend (Next.js) и backend API (FastAPI).
2. Аутентификация, авторизация, роли и права доступа.
3. Реестры: оборудование, инспекции, нарушения, акты, задачи, разрешения.
4. Карта цеха с редактированием элементов и фоновым изображением.
5. AI-функции с использованием базы знаний (RAG-подход).
6. Дашборды, аналитика, отчеты, экспорт.
7. Журналы аудита и мониторинг ошибок.
8. Контейнеризация и запуск в Docker.

### Не входит в проект
1. Мобильное нативное приложение (iOS/Android).
2. Интеграции с ERP/1С/SCADA (кроме оговоренных отдельно).
3. Полноценный BI-контур вне встроенных отчетов.

## 4. Роли пользователей и права
1. `admin` — полный доступ ко всем разделам и настройкам.
2. `manager` — управление и контроль показателей, просмотр/коррекция данных.
3. `inspector` — проведение инспекций, фиксация нарушений, работа с актами.
4. `operator` — операционные действия в назначенных разделах.
5. `auditor` — доступ к журналам и отчетности, без критических изменений.
6. `viewer` — просмотр данных без права изменения.

## 5. Функциональные требования
### 5.1 Аутентификация и безопасность
1. Вход по логину/паролю.
2. JWT access token и refresh token.
3. Ролевой контроль доступа (RBAC) на backend-уровне.
4. Выход из системы с инвалидированием refresh-токена.
5. Защита API от неавторизованного доступа.

### 5.2 Пользователи и роли
1. Создание/редактирование пользователей (для администратора).
2. Назначение ролей и прав.
3. Логирование действий по управлению пользователями.

### 5.3 Реестр оборудования
1. CRUD по оборудованию.
2. Хранение паспортных и инвентарных данных, статуса, местоположения.
3. Привязка оборудования к цеху и карте.
4. Фильтрация, поиск, сортировка.

### 5.4 Чек-листы и инспекции
1. Создание шаблонов чек-листов и пунктов.
2. Проведение инспекций по оборудованию.
3. Фиксация ответов, замечаний и вложений.
4. Перевод инспекции в статусы выполнения.

### 5.5 Нарушения
1. Создание нарушения вручную и из инспекции.
2. Классификация по критичности, типу, статусу.
3. SLA-дедлайн с ручным и автоматическим расчетом.
4. Изменение статуса нарушения и фиксация закрытия.
5. Экспорт списка нарушений в читаемом табличном формате на русском языке.

### 5.6 Акты и документы
1. Формирование актов по нарушениям.
2. Хранение номера, даты, статуса и содержимого акта.
3. Экспорт и печатная форма актов.

### 5.7 База знаний и AI-помощник
1. Ведение базы знаний нормативных документов.
2. AI-ассистент использует релевантные фрагменты базы знаний.
3. При пустом результате поиска AI должен явно сообщать об отсутствии источников.
4. Запрет на вымышленные нормативные ссылки без подтвержденного источника.
5. Поддержка сценариев AI 2.0:
6. `создать план устранения`;
7. `подготовить отчет`;
8. `сформировать список контрольных вопросов`.

### 5.8 Карта цеха
1. Выбор/создание цеха и этажей.
2. Слои и элементы карты: оборудование, стены, зоны, колонны, текст, ластик.
3. Импорт подложки (PNG/SVG и др. в рамках поддерживаемых форматов).
4. Привязка к сетке, масштаб, контраст, сохранение состояния.
5. Отображение подсказок элементов при просмотре.

### 5.9 Дашборд
1. KPI по нарушениям, инспекциям, статусам.
2. Блок рисков оборудования (Top-N).
3. Блок SLA-алертов и просрочек.
4. Быстрый переход к проблемным объектам.

### 5.10 SLA и оповещения
1. Правила SLA по типу/критичности нарушения.
2. Периодическая проверка просрочек и ближайших дедлайнов.
3. Создание алертов (`SLA_OVERDUE`, `SLA_WARNING`).
4. Подтверждение алертов пользователем.

### 5.11 Аудит и мониторинг ошибок
1. Журнал действий пользователей.
2. Журнал событий ошибок backend (код, сообщение, trace_id, путь, метод, статус).
3. Сводка ошибок и фильтрация.
4. Пометка ошибок как обработанных.
5. Прослеживаемость через trace_id.

### 5.12 Задачи, разрешения, workflow
1. Задачи с назначением ответственных и сроками.
2. Разрешения на работы и жизненный цикл статусов.
3. Маршрутизация процессов через workflow-операции.

### 5.13 Файлы и вложения
1. Загрузка файлов к оборудованию, инспекциям, нарушениям, актам, задачам.
2. Хранение метаданных и ограничений по типам.
3. Скачивание и просмотр файлов.

### 5.14 Отчеты и экспорт
1. Генерация отчетов по ключевым сущностям.
2. Экспорт с русскими названиями полей и понятной структурой.
3. Форматы: минимум XLSX/PDF/CSV по доступным разделам.

## 6. Нефункциональные требования
### 6.1 Производительность
1. Время ответа API для типовых запросов: до 2 секунд при штатной нагрузке.
2. Долгие операции должны выполняться асинхронно либо с понятной индикацией.

### 6.2 Надежность и устойчивость
1. Retry и timeout для ошибок подключения к БД.
2. Circuit breaker для AI-интеграций.
3. Graceful fallback при недоступности внешних сервисов.

### 6.3 Безопасность
1. Ролевой контроль на каждом защищенном endpoint.
2. Хранение секретов только в переменных окружения.
3. Refresh token в защищенном режиме хранения.
4. Логи не должны содержать секреты и токены.

### 6.4 Логирование и наблюдаемость
1. Единый формат ошибок API с `code`, `message`, `trace_id`, `retryable`.
2. Структурированное логирование основных событий.
3. Технические health-check endpoints.

### 6.5 Кодировки и локализация
1. Все текстовые данные и ответы API в UTF-8.
2. Интерфейс и экспортные формы на русском языке.

## 7. Техническая архитектура
1. Frontend: Next.js (React, TypeScript).
2. Backend: FastAPI (Python 3.11).
3. ORM: SQLAlchemy (async), драйвер asyncpg для PostgreSQL.
4. БД: PostgreSQL (основная), SQLite только для локального fallback.
5. Контейнеризация: Docker.
6. AI-провайдеры: настраиваемые через env (OpenAI/Timeweb и др.).

## 8. Ключевые сущности данных
1. `users`, `roles`, `user_roles`, `refresh_tokens`.
2. `equipment`, `equipment_history`.
3. `checklist_templates`, `checklist_items`, `inspections`, `inspection_answers`.
4. `violations`, `violation_sla_rules`.
5. `acts`, `act_violations`.
6. `knowledge_base`.
7. `files`.
8. `tasks`, `permits`, `notifications`.
9. `audit_logs`, `alerts`, `error_events`.
10. `workshop_maps`, `system_settings`, `analytics_cache`, `reports`.

## 9. API-требования
1. Все API доступны под префиксом `/api/*`.
2. Обязательная проверка прав для защищенных маршрутов.
3. Единая схема ошибок и возврат `trace_id` в заголовке ответа.
4. Базовые группы endpoint: `auth`, `users`, `equipment`, `inspections`, `violations`, `acts`, `knowledge`, `files`, `reports`, `alerts`, `audit`, `workflow`, `workshop-map`.

## 10. Развертывание и окружения
1. Окружения: `dev`, `stage`, `prod`.
2. Docker-образ приложения с backend и frontend.
3. Конфигурация через переменные окружения (`SECRET_KEY`, DB-параметры, AI-параметры, CORS).
4. Health-check: `/api/health`.
5. Порты по умолчанию: frontend `3000`, backend `8000`.

## 11. Тестирование и приемка
### 11.1 Обязательные виды тестов
1. Unit-тесты бизнес-логики.
2. Integration-тесты API и БД.
3. E2E-тесты ключевых пользовательских сценариев.

### 11.2 Критерии приемки
1. Пользователь может пройти путь: оборудование → инспекция → нарушение → акт.
2. SLA-алерты формируются автоматически и отображаются в UI.
3. AI-ответы содержат источники или явное сообщение об их отсутствии.
4. Аудит и мониторинг ошибок фиксируют события с trace_id.
5. Экспорт формируется корректно и на русском языке.
6. Система запускается в Docker и проходит health-check.
